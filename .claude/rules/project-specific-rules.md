# Project-Specific Rules

> Rules unique to the IndiaMart Clone project — domain logic, business constraints, and architectural decisions.

---

## Domain Rules

### User Roles
- Every account is a **buyer** by default at registration.
- A buyer upgrades to **seller** via `POST /auth/upgrade-to-seller` — this rotates the token pair.
- **Admin** accounts are created only via the seeder (`ADMIN_EMAIL` env var) — never via a public API.
- Role hierarchy: `buyer ⊂ seller ⊂ admin` — every seller is also a buyer.

### Products
- Slugs are generated server-side from `name` via `slugify` + uniqueness retry loop. Never accept client-supplied slugs.
- `view_count` is incremented fire-and-forget — never block the product detail request on it.
- Ownership is checked via `ProductsService.assertOwnerOrAdmin()` — not via a guard.
- Product images attach separately after product creation via `POST /products/:id/images`.
- `stock_status` is an enum: `in_stock | out_of_stock | on_demand`.

### Sellers / Supplier Profiles
- `seller_profiles.slug` is the public identifier for supplier pages (`/suppliers/:slug`).
- `is_verified` flag is toggled only by admins via `PATCH /admin/suppliers/:id/verify`.
- The multi-step seller signup modal uses the `general` fallback category when no category is chosen.

### Inquiries
- Any authenticated user can send an inquiry — not just buyers.
- Inquiry list is role-scoped:
  - Buyer sees what they sent.
  - Seller sees what they received.
  - Admin sees everything.
- `last_read_at` per side powers the unread-count badge on the navbar.
- Inquiry thread replies go to `POST /inquiries/:id/reply`.

### Requirements (Buy-Leads)
- Any authenticated user can post a requirement.
- Sellers see the feed via `GET /requirements/feed` — this excludes their own posts.
- A seller responds to a requirement via `POST /requirements/:id/respond` — this atomically creates an inquiry with the buyer's requirement as context.
- Requirements have status: `open | closed`.

### Search
- `GET /search?q=&type=all` returns max 8 products + 8 suppliers + 8 categories.
- `GET /search?type=products` or `type=suppliers` returns paginated results.
- `GET /search/suggest` returns max 5 hits of each type — used for navbar autocomplete.
- Fuzzy matching uses `pg_trgm` trigram GIN index on `products.name`.

### Uploads
- **Always** call `GET /uploads/status` before uploading to know if S3 or local-disk is active.
- S3 flow: `POST /uploads/presign` → PUT directly to S3 URL → `POST /products/:id/images` with the `s3Key` + `url`.
- Local-disk flow: `POST /uploads/file` multipart → `POST /products/:id/images` with the returned `url`.
- Accepted MIME types: `image/jpeg`, `image/png`, `image/webp`, `image/gif`.

## Architecture Constraints

### Database
- PostgreSQL 16 with `uuid-ossp`, `pg_trgm`, `unaccent` extensions — these are bootstrapped by `docker/init.sql`.
- All PKs are `UUID` generated by `uuid-ossp`.
- Every table has `created_at` + `updated_at`. Paranoid (soft-deleted) tables also have `deleted_at`.
- Migration naming: `XXXX-<verb>-<subject>.ts` (e.g. `0013-add-phone-to-users.ts`).
- Migration sequence is zero-padded to 4 digits.
- Seeders are idempotent — safe to run multiple times.

### Auth Architecture
- **Two JWT secrets**: `JWT_SECRET` (access, 15m) and `JWT_REFRESH_SECRET` (refresh, 7d).
- Leaking one secret does not compromise the other.
- Refresh token is rotated on every successful `/auth/refresh` call.
- bcrypt rounds = 12. Do not change without a password re-hash migration plan.
- The frontend's axios interceptor short-circuits when the failing call is itself `/auth/refresh` to avoid infinite loops.

### Monorepo
- npm workspaces: `frontend` and `backend` are the two workspaces.
- No Turborepo — revisit if CI build times exceed 5 minutes.
- All root-level scripts delegate to workspaces (`--workspace=frontend`, etc.).

## What NOT to Do

- ❌ Don't add a `pages/` directory to the frontend — App Router only.
- ❌ Don't use `getServerSideProps` or `getStaticProps` — those are Pages Router APIs.
- ❌ Don't add a new seeder for data that should be in a migration (schema ≠ seed data).
- ❌ Don't expose Swagger in production (`SWAGGER_ENABLED=false`).
- ❌ Don't allow the seller upgrade endpoint to be called by an account that is already a seller.
- ❌ Don't use `Model.update()` for bulk operations without a `where` clause — this will update every row.
- ❌ Don't add a new npm package without checking if the functionality already exists in the project.
